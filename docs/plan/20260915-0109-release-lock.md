## Proposal

1. `tools/check-lock.sh lock|upstream|pins`: the file rules of sections 1, 4
   and 4.1; `tests/vectors/` copies the spec's lock, upstream and pins vectors
   and `tests/lock-test.sh` runs them against `expected.tsv`.
2. Inputs: `locks/mica-build-env.lock`, `locks/mica-system-base.lock` and
   their pins, committed unchanged. `tools/inputs.sh` replaces
   `tools/build-env.sh`: `check` (file rules, offline), `verify [<repository>]`
   (the release's `SHA256SUMS` hashes to the pin, lists only the lock, and the
   lock downloads with the same bytes), `image <name>` (a build-env index
   reference) and `upstream-image <name>` (an upstream row of the build-env
   lock). Every third-party image reference in the tree must be such a row.
3. `locks/upstream.lock`: the six upstream trees as `git` rows (tag, commit);
   the Dockerfile verifies each clone's commit. `versions.env`,
   `versions-stamp.sh`'s input and the shipped `versions.env` become
   `locks/upstream.lock`; the package version comes from the podman row's tag.
   `debian-packages.lock` becomes `source` rows of `locks/upstream.lock` under
   the Base apt URI. `tools/base-check.sh` reads the Base rootfs `image` rows,
   the `upstream` rows and the `apt` row (rendered as the deb822 source).
4. Writer: `tools/release.sh` publishes the pools (source annotations added),
   reads them back anonymously, then attaches exactly `mica-podman.lock`
   (`release`, `pool` amd64/arm64, `package` per architecture) and
   `SHA256SUMS` listing it; no deb assets, no `podman-pkgs.lock`.
5. `make offline` keeps working on the new inputs; README, changelog.
6. Gates, push, CI, then `gh release create`, follow `release.yml`, verify
   anonymously.

## Risks

- The shipped `/usr/share/mica-podman/versions.env` becomes
  `/usr/share/mica-podman/upstream.lock`; mica-build's podman check must follow.
- First publish creates `ghcr.io/micaoss/mica-podman` private.
